1. Executive Summary

CrossLayerAI-RAN is an unsupervised anomaly detection system built to proactively identify hardware distress in high-performance computing (HPC) clusters, developed under the Samsung Research Institute Bangalore (SRIB) PRISM program. The system processes over 180GB of real-world Prometheus telemetry collected from a Jefferson Lab HPC cluster, spanning four infrastructure layers — CPU, Memory, Disk, and SLURM job-scheduler data — to learn a model of "normal" cluster behavior without ever being shown a labeled failure. When live infrastructure metrics drift meaningfully from that learned baseline, the system flags the deviation as a likely hardware fault before it escalates into a full outage.

Four unsupervised models — Isolation Forest, Local Outlier Factor (LOF), a neural Autoencoder, and a majority-vote Ensemble — are trained independently per hardware farm and per telemetry modality. Evaluated against a single real, IT-confirmed hardware distress event, the system achieved up to 100% recall on the strongest-performing farm/model combination, with several other farm/modality pairs exceeding 90% recall.

The project delivers a full reproducible data pipeline, a public results dashboard, and a live interactive Streamlit application that lets a reviewer inject synthetic hardware faults in real time and watch two independently trained models agree on the verdict.

2. Problem Statement

Modern HPC and RAN infrastructure clusters generate enormous volumes of low-level telemetry, but hardware failures are rare, expensive to label, and often develop gradually before manifesting as a visible outage. Traditional supervised anomaly detection requires labeled failure examples that, in practice, rarely exist in sufficient quantity or diversity to train a reliable classifier.

This project addresses the harder, more operationally realistic version of the problem: can a system learn what "normal" infrastructure behavior looks like directly from unlabeled telemetry, and reliably flag meaningful deviations, with zero labeled failure examples used during training?

3. Dataset

  • Source: Jefferson Lab HPC cluster, Prometheus-format telemetry exports
  • Size: 180GB+ raw, compressed .csv.gz files
  • Time window: May 19–23, 2023
  • Modalities: CPU utilization, Memory, Disk I/O, SLURM job-scheduler state
  • Hardware farms: 5 clusters — farm14, farm16, farm18, farm19, farm23
  • Ground truth: one real, Jefferson Lab IT-confirmed hardware distress event on May 23, 2023, used exclusively for evaluation, never for training
  • Known coverage gap: CPU and Disk telemetry has an approximately 84% scraping gap on May 23 due to a Prometheus collection interruption; these two modalities are evaluated via cross-referenced SLURM distress signals rather than direct ground truth on the event day

4. Methodology

4.1 Chronological Split Design

The train/test split is chronological, not random — a deliberate design choice to prevent the anomalous day from leaking into training:

  • Train: May 19 00:00 – May 22 23:59 (normal operation only)
  • Test: May 23 00:00 – May 23 23:59 (the real anomalous day)
  • Validation: none — an unsupervised pipeline has no labels to tune a validation split against
An earlier iteration of this pipeline used a random 70/15/15 split, which leaked May 23 anomalous data into both training and validation. This was identified and corrected before any model results were finalized — see Section 8.

4.2 Pipeline Stages

  • 1. Structural Cleaning — chunk-wise streaming ingestion of raw telemetry, junk-column pruning, timestamp parsing, deduplication.
  • 2. Chronological Split — described in Section 4.1.
  • 3. Train-only Normalization — IQR bounds and z-score statistics computed exclusively on training data, then applied uniformly to avoid leakage.
  • 4. Feature Engineering — rolling-window statistics (5/15/60-minute mean, standard deviation, min, max) and lag-1 differences per node and signal.
  • 5. Multimodal Join — Memory and SLURM telemetry joined on (node, timestamp) to construct cross-layer features.
  • 6. Multimodel Training — Isolation Forest, LOF, Autoencoder, and Ensemble trained independently per hardware farm.

5. Model Architecture

  • Isolation Forest — tree-based ensemble; contamination parameter 0.05; trained on PCA-reduced features (95% explained variance retained) for the CPU and Disk modalities.
  • Local Outlier Factor (LOF) — density-based detector; flags points that are significantly less dense than their local neighborhood.
  • Autoencoder (ReconAE) — a compact MLP-based reconstruction network (hidden-layer sizing scaled to input dimensionality, ReLU activation, Adam optimizer, early stopping). Anomaly threshold is set at the 99th percentile of training reconstruction error on most farms — 85th percentile for farm19, deliberately loosened for higher recall.
  • Ensemble — majority vote (≥ 2 of 3 models) trading peak recall for robustness against any single model's blind spots.

6.4 Key Observations

  • No single model dominates across all farms and modalities — the strongest justification for the ensemble approach.
  • Precision remains in the single digits across most farm/model combinations. This is an expected and explicitly acknowledged consequence of unsupervised evaluation against a single labeled event, with no negative examples available for threshold tuning.
  • Inference latency is sub-millisecond per row for tree- and MLP-based models, indicating real-time deployment feasibility.
  • farm23 records 0% recall across every modality because it has zero real distress events in its test window — an artifact of the data, not a model failure.

7. Live Interactive Demonstration

A three-tab Streamlit application, deployed publicly, provides:

  • Results Dashboard — full metrics tables and comparison charts across all farms, models, and modalities.
  • Time-Series Scores — reconstruction error across the full test window with the trained anomaly threshold overlaid, plus a node-level heatmap of the real May 23 event.
  • Live Anomaly Injection Playground — lets a reviewer synthetically perturb a "normal" data point along five fault dimensions (CPU spike, memory leak, I/O thrashing, job flood, sensor noise) and observe two independently trained models — the Autoencoder and Isolation Forest — verify the resulting verdict in real time, against each model's own genuinely trained threshold.

8. Engineering Challenges

  • Large-scale data processing — 180GB+ of compressed telemetry required chunk-wise streaming ingestion to avoid memory exhaustion on standard hardware.
  • Data leakage in the initial split — an early random 70/15/15 split leaked anomalous May 23 data into training and validation, which would have made evaluation results artificially optimistic. This was identified and corrected via a strictly chronological split before any results were finalized.
  • Absence of ground-truth labels — SLURM distress states were used only as a post-hoc evaluation proxy, never during training, to preserve a genuinely unsupervised setup.
  • CPU/Disk telemetry coverage gap — an ~84% Prometheus scraping gap on the event day required cross-referencing SLURM distress signals for indirect evaluation of these two modalities.
  • High dimensionality — rolling-window and lag feature engineering produced 600+ raw features; PCA and per-modality scaling were applied to preserve model reliability, particularly for LOF and Isolation Forest.
  • Per-farm threshold tuning — farm19 required a looser 85th-percentile threshold (versus 99th elsewhere) to achieve usable recall, illustrating the precision/recall tradeoff inherent to unsupervised thresholding.

9. Limitations

  • Low precision — single digits in most farm/model combinations. This is the primary open problem, a direct consequence of unsupervised evaluation against one labeled event with no negative examples to tune against.
  • No temporal modeling — each telemetry row is scored independently; the system does not yet model gradual drift over time.
  • Independent per-modality models — CPU, Memory, and Disk are trained as separate models rather than fused into a single joint model, despite the cross-layer thesis of the project.
  • Single-event evaluation — generalization to other, different failure modes is not yet empirically validated beyond the one real event in this dataset.

10. Future Work

  • Temporal modeling — an LSTM- or Transformer-based Autoencoder to capture drift over time rather than scoring isolated points.
  • True multivariate fusion — a single joint model across CPU, Memory, Disk, and SLURM instead of four separate per-modality models.
  • Precision improvements — per-farm adaptive threshold tuning and temporal smoothing (alerting only on sustained, multi-window anomalies).
  • Node-level aggregation and explainability — flag anomalous nodes rather than anomalous rows, and surface which features drove a given flag (e.g., SHAP-based attribution).
  • Additional real-world validation — evaluation against further confirmed anomaly events as they become available.
  • Streaming inference — deployment as a real-time, online scoring service rather than a batch pipeline.

11. Conclusion

CrossLayerAI-RAN demonstrates that a fully unsupervised, multi-model pipeline can reliably detect real hardware distress events in large-scale HPC telemetry without ever training on a labeled failure — achieving up to 100% recall on the strongest farm/model combination while remaining transparent about its current precision limitations.

The project delivers a reproducible data pipeline, a public results dashboard, and a live interactive demo that allows independent verification of the system's behavior under synthetic fault conditions — providing a solid technical foundation for the cross-layer, infrastructure-aware anomaly detection approach central to the SRIB-PRISM worklet objectives.
